## Design Specificity Verdict

Authored for this product: the OKLCH token system with hue-role discipline, the echo/template
vocabulary, and per-destination setup docs are specific, not template-derived. The visual skin is
utilitarian by design, appropriate for an Operate-surface SaaS at this stage.

Deterministic scan (B): 2 findings, both real: overused-font (Inter is the literal first face —
a deliberate, defensible choice at this stage; revisit when the brand wants more character) and
em-dash-overuse in howto.html (10 em-dashes, advisory severity). A11y probes: 0 missing alt,
0 unlabeled inputs, 0 unlabeled buttons. Mobile 390px: no horizontal overflow on landing,
dashboard, feeds.

## Overall Impression

The dark theme is genuinely excellent and the app's a11y fundamentals are stronger than most
betas. The light theme, however, fails WCAG AA on its accent system — links, buttons, badges,
and alerts — which is the single biggest credibility gap for a product with a free trial.

## What's Working

1. Dark theme contrast is exemplary: body 14.59:1, muted 6.43:1, accent links 8.7:1.
2. A first-class How To page in the primary nav with per-destination setup — exactly what a
   multi-destination cross-poster needs.
3. The /echoes composer is genuinely powerful while staying one form: documented template
   variables, include/exclude filters, content warning, attach-image, drip/digest, Preview.

## Priority Issues (verified)

1. [P0] Light theme fails WCAG AA on its accent system. Browser-verified pairs: accent links
   4.10:1 (need 4.5), CTA/primary button text 4.43:1, success badge text 3.55:1, accent badge
   3.59:1, warning badge 2.88:1, dark-theme danger alert text 3.25:1. Users on light system
   themes get unreadable links, buttons, and badges. Fix: raise lightness (or swap to a
   contrast role) for light-theme --accent/--primary/--success/--warning and their washes,
   and add a per-theme contrast matrix to CI so themes cannot drift apart again.
2. [P1] Anonymous 404 silently redirects to /login (verified: 302 with a browser Accept
   header, no 404 page, no message). A visitor following a bad link cannot distinguish
   "page doesn't exist" from "session expired". Fix: real 404 page for unknown routes;
   redirect only known-but-protected routes with a "log in to continue" notice.
3. [P1] /register requires an invite code with zero guidance (verified live: field renders,
   required, no hint of where to get one). The "Start your free trial" CTA leads to a form
   that cannot be completed without out-of-band knowledge. Fix: inline help ("request a code
   at ...") or a request-code flow, or confirm the gate is intentional and gate the CTA too.
4. [P3] Admin plan/promote/extend-trial/unsuspend actions have no confirm (suspend, demote,
   and invite-revoke do). Plan changes can alter a paying user's billing. Fix: extend the
   existing confirm pattern to plan and promote.
5. [P3] Dark-theme danger alert text on wash at 3.25:1 (fold into the P0 contrast pass).

## Minor Observations

- howto.html uses 10 em-dashes (advisory; also inconsistent with the author's own style).
- Every page's DOM contains two identical /logout forms.
- Auth pages use the brand "FeedEcho" as their H1 instead of a task label.
- Theme toggle is a bare glyph button with no visible text.
- /reset-password with no token shows a bare error with no link back to /forgot-password.
- Inter is the literal first font face — deliberate but the detector's canonical tell; fine for
  a utilitarian beta, worth revisiting when branding matures.

## Questions to Consider

- What would a live status strip (last polled / next poll / last posted) on the dashboard do
  for user trust?
- Is the invite gate a waitlist in disguise — and if so, should the CTA say so?
- Could the light theme share the dark theme's contrast roles instead of its own tokens?
